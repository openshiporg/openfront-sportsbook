## Blockers

### QA-001: Finishing MFA enrollment or step-up signs the operator out, so no platform screen can ever be used
- **Area:** onboarding / dashboard
- **URL:** `/dashboard/platform/security`, then every `/dashboard/platform/*`
- **Steps:**
  1. Sign in as a new admin. Every platform page (Control room, Catalog, Onboarding, Settings…) shows "MFA verification required".
  2. Open Operator security, click **Begin enrollment**, enter a valid TOTP code, click **Verify and enable**.
  3. Sign in again. Security now says "Enrolled · session not verified". Enter a valid TOTP code and click **Verify session**.
- **Expected:** step 2 shows the 8 recovery codes and leaves the operator signed in with an MFA-verified session. Step 3 verifies the session, and platform screens load.
- **Actual:** both steps redirect straight to `/dashboard/signin?from=…`. The recovery codes are never shown: they are generated, hashed and stored, but the page that displays them is lost when the session ends, so the operator has none. Signing in again gives an unverified session, and step-up signs you out again. Onboarding, Store Settings, Catalog, Trading, Customers, Finance and the other platform screens can't be reached. The sportsbook can't be set up at all.
- **Likely cause:** `features/keystone/session-assurance.ts` `startOperatorMfaSession()` seals `{ itemId, operatorMfaAssurance }` **without `listKey: 'User'`**. `@keystone-6/auth` only resolves a session whose `listKey` matches (`authenticatedItem` returns null when `session.listKey !== listKey`), so the new cookie set by `features/platform/security/actions.ts` (`completeMfaEnrollment`, `verifyMfaSession`) counts as signed out. Fix: include `listKey: 'User'` in the sealed data, then re-test enrollment, step-up, and showing the recovery codes.
- **Note:** the existing QA admin is already enrolled with no recovery codes. Use the stored TOTP secret for step-up after the fix.

### QA-002: Generic list, item and create pages are broken because the view order doesn't match the schema
- **Area:** dashboard
- **URL:** `/dashboard/<list>` (126 of 130 lists), `/dashboard/users/<id>`, `/dashboard/<list>/create`
- **Steps:** open `/dashboard/users`, `/dashboard/competitions`, `/dashboard/wagers`, etc. Then open your own user at `/dashboard/users/<id>`. Then open `/dashboard/sports/create`.
- **Expected:** lists show rows and empty states, the item page shows the user, and create forms use the right control for each field.
- **Actual:**
  - 126 lists show "Failed to load items: Unable to complete the request. Please try again." Only Jurisdictions, Tenants and Currency Definitions load. Resettlement Cases redirects to `/dashboard`.
  - `/dashboard/users?fields=name,email` works, but `?fields=name,role` or `?fields=name,tenant` fails. So any relationship, timestamp or checkbox column breaks the query.
  - Your own user's item page says "Not found… doesn't exist, or you don't have access to it".
  - On Create Sport, **Tenant** (a relationship) renders as a JSON textarea with `{"key": "value"}`, and **Active** (a checkbox) renders as an empty grey relationship box. The User and Role create forms have the same problem.
- **Likely cause:** `features/keystone/view-order/index.ts` has `VIEW_ORDER = [text, password, relationship, timestamp, select, checkbox, json, integer]`. The live admin meta reports `viewsIndex` as: 1 text, 2 timestamp, 3 checkbox, 4 json, 5 integer, 6 password, 7 relationship, 8 select. `features/dashboard/views/getFieldTypeFromViewsIndex.ts` therefore maps relationship to json (no sub-selection, so the GraphQL query is invalid), timestamp to password (`createdAt { isSet }`), and checkbox to relationship. The B5-B6 report says this file was "restored"; it was restored to a stale order. Regenerate it with `features/keystone/view-order/generate-view-order.ts` (run as part of `npm run migrate:gen`) and commit the output.

### QA-003: The deployed storefront has no brand colours, so headings, buttons and the header are white on white
- **Area:** storefront (every page, both widths)
- **URL:** `/`, `/account/auth`, `/account/disputes`, `/account/security`, etc.
- **Steps:** open `/` at 1440px or 390px.
- **Expected:** the night price board: `bg-sb-night` header, chalk `bg-sb-paper` page, cobalt primary pills, lime/red accents, `.sb-tear` ticket notches.
- **Actual:**
  - The header is white, so the white logo wordmark, nav labels and **Sign in** pill are invisible.
  - The page titles "LIVE & UPCOMING" and "BETTING CLOSED", the bet-slip heading, and every primary button ("Create account", "Send request", "Sign in or recover") are white text on white.
  - The search field and nav tracks render as flat grey slabs.
  - On desktop, the home page looks like an empty grey search bar next to a box that says "No selections".
- **Evidence:** the HTML uses `bg-sb-night`, `bg-sb-paper`, `text-sb-ink` and `bg-sb-well`. The served CSS (`/_next/static/chunks/0ypk28500ule8.css`, and `2669ftlxbhu16.css` on the dashboard) has **no** `bg-sb-*` or `text-sb-*` rules, no `--color-sb-*` theme variables, and no `.sb-tear` rule. Arbitrary classes from the same commit (for example `max-w-[1560px]`, and gradients that use `var(--color-sb-brand)`) *are* present. So the 50 lines added to `app/globals.css` (the `@theme { --color-sb-… }` block and `.sb-tear`) never reached the deployed bundle.
- **Likely file:** `app/globals.css` (lines ~140–192), and the deployment itself. Run a local `next build`, check whether the chunk has `.bg-sb-night`, and check which commit Railway built. If a local build has the rules, redeploy. If it doesn't, move the tokens into the `@theme inline` block, or check the Tailwind v4 handling of a second `@theme` after `@layer base`.

### QA-004: The storefront can't take accounts, prices or bets in production (sandbox gate)
- **Area:** storefront
- **URL:** every customer page. `/api/sandbox/sportsbook/*` returns `{"error":"SANDBOX_DISABLED"}` with HTTP 404.
- **Steps:** open `/`, then try **Start guest account**, Create account or a support request.
- **Expected:** a customer can register, browse priced events, build a slip and place a practice bet.
- **Actual:** "Betting closed · Accounts, prices and bets are unavailable". Registration says "Registration is unavailable until the operator publishes its terms" and the terms checkbox stays "Loading revision…". A guest account fails with "Couldn't create the account: SANDBOX_DISABLED".
- **Likely file:** `features/sportsbook/api/sandbox-policy.ts` `assertSandboxRuntime()`. Already flagged in `sportsbook-REDESIGN-READY.md` as an owner decision. It's still a blocker for any storefront QA or for a merchant going live. It needs either the owner-approved gate change or an isolated sandbox environment. Even with the gate open, terms can only be published through the operator dashboard, which QA-001 blocks.

## Major

### QA-005: Dashboard home shows "Unknown" for all 130 model counts
- **Area:** dashboard
- **URL:** `/dashboard`
- **Steps:** sign in and open `/dashboard`.
- **Expected:** item counts ("1 item", "0 items"), as in E-commerce.
- **Actual:** every card says "Unknown". Each `…Count` query works on its own from the browser.
- **Likely cause:** `features/dashboard/actions/getListCounts.ts` sends one query with 130 aliases (`User: usersCount`…). `features/sportsbook/api/graphql-query-guard.ts` caps `MAX_GRAPHQL_QUERY_ALIASES = 100`, so the request is rejected with "Query exceeds limits". Fix: batch the counts into chunks of 100 or fewer, or skip aliases. Don't raise the guard without a reason.

## Business sense (day one for a sportsbook operator)

- An operator can't get from "account created" to "tenant configured". That's QA-001. Until it's fixed there's no way to add a brand, publish terms, set a jurisdiction, connect a feed, or create a sport or market.
- Customer registration depends on published terms (correct for a regulated product), but the operator UI that publishes them is behind QA-001. Fix both, then retest registration end to end.
- There's no deposit or withdrawal path to Stripe or any PSP. The wallet is "Practice funds" only, which fits the README's practice-play position. If the product is ever meant to take real money, it needs payment-provider onboarding similar to E-commerce's Stripe setup.
- The responsible-gaming surfaces (Safer play, limits, self-exclusion, account closure) exist on the storefront, which is the right day-one set. They couldn't be exercised (QA-004).
