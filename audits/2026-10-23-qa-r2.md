## Blockers

### QA-016: The Approval inbox crashes, so no dual-control request can be approved and results can't be graded or settled
- **Area:** dashboard
- **URL:** `/dashboard/platform/approvals` (signed in as an operator with `canApproveSensitiveActions` and an MFA-verified session)
- **Steps:**
  1. As QA Admin, enter a pending result for an event on Result approval, and click **Request independent approval** (it succeeds: "Approval pending · Decided by another user").
  2. Bootstrap an independent approver on Roles, sign in as them, and enroll MFA (works).
  3. Open **Approval inbox**.
- **Expected:** the pending result approval, with Approve / Reject.
- **Actual:** "This page couldn't be loaded. Try again, or sign in again if your session has expired." Reloading gives the same result. Console: `Minified React error #31 … object with keys {message, extensions}`, so a GraphQL error object is being rendered as a React child. Other screens work for the same user (Security shows "session verified"; Catalog and Finance correctly say "No access").
- **Impact:** every dual-control flow goes through this inbox: result approval, setting changes, role grants, operator admission, overrides and resettlements. In this run it stopped the main workflow at "result pending". Grading, settlement and payout were never reached.
- **Likely files:** `features/platform/approvals/ApprovalsScreen.tsx` and `screens/ApprovalsPageClient.tsx` (find where a GraphQL `errors[0]` object, rather than its `.message`, reaches JSX, possibly via `MutationForm` state or a prop built from a keystoneClient error). Also check the platform `error.tsx` boundary. Reproduce with `next start` and an approver session to get the unminified error.

## Major

### QA-017: Onboarding never finishes: the Promotions stage fails with "Unexpected error." and the operator is stuck at 8/9
- **Area:** onboarding
- **URL:** `/dashboard/platform/onboarding`
- **Steps:** on a tenant-less, MFA-verified admin, fill New operator and click **Configure sandbox operator**. Then click **Resume setup**.
- **Expected:** "Configured", 9/9 stages, and `onboardingStatus` completed.
- **Actual:** the form shows "Unexpected error." (GraphQL `applySportsbookOnboarding` returns `{"message":"Unexpected error."}`). The serializable transaction did commit, so the tenant, brand, adapters and catalog exist, but the page reads "8/9 stages complete · next Promotions" and Promotions stays `pending`. **Resume setup** fails the same way every time. The sidebar welcome card still says "Your sportsbook is empty. Set up the operator tenant…" with **Get started**, because the user stays `in_progress`.
- **Cause:** `features/keystone/mutations/sportsbook.ts` (around line 153) calls `ensureSandboxPromotions()` after the transaction. `features/sportsbook/customer/promotions.ts:19` starts with `assertSandboxEnabled()`, which throws `SANDBOX_DISABLED` in production (QA-004). Provisioning operator-side promotion fixtures shouldn't depend on the customer sandbox gate. Either skip the sandbox promotions when the customer API is off and mark the stage complete or "not applicable", or drop the assert from the operator path. Also map known codes to readable onboarding errors instead of Keystone's masked "Unexpected error.".

### QA-018: Store Settings branding never reaches the storefront
- **Area:** storefront / dashboard
- **URL:** `/dashboard/platform/settings`, then `/`
- **Steps:** onboard with brand "QA Sportsbook". Settings shows the preview header "QA SPORTSBOOK". Open the storefront.
- **Expected:** the storefront header, logo, hue and page titles use the configured brand.
- **Actual:** the header says "SPORTSBOOK" with the default logo, and every title is "… · Sportsbook" (the fallback).
- **Cause:** `features/storefront/lib/data/brand.ts` resolves the brand through `resolveSandboxTenant`/`resolveSandboxBrand` (`features/sportsbook/api/sandbox-tenant`), which only match the `sportsbook.local` sandbox domain. That throws in production and the function returns `null`. The storefront should read the install's operator brand (by request host, or the single active brand) independently of the sandbox gate. This is the same change as item (a) in the r1 QA-004 notes, but it matters even while betting is closed.

### QA-019: A result can be entered for an event that hasn't started
- **Area:** dashboard (business)
- **URL:** `/dashboard/platform/results?eventId=cmvlm97d6003xqm01tnuyzheg`
- **Steps:** create an event starting in two days (status `scheduled`, market open and priced). On Result approval it's listed under "Enter result · 1 eligible". Set the outcomes and click **Enter pending result**.
- **Expected:** results can only be entered once the event is ENDED (or at least past its start time), and the market should be closed or suspended first.
- **Actual:** "Pending result version entered." for a match two days away while its market is still open for betting. Combined with approval, that lets wagers be graded before kick-off.
- **Likely files:** `features/platform/results/ResultsScreen.tsx` (eligible statuses `SCHEDULED, LIVE, ENDED` at lines ~30/35/52) and the result-entry mutation in `features/keystone/mutations/sportsbook.ts`. Enforce the rule on the server, not only in the list.

### QA-020: Trading has no usable manual pricing, and new markets open unpriced
- **Area:** dashboard (business)
- **URL:** `/dashboard/platform/catalog` (Create event), `/dashboard/platform/trading/<marketId>`
- **Steps:** create an event with a market, then try to price it.
- **Expected:** a trader sets the odds for each selection in one form (as on any sportsbook back office), and a new market starts suspended until it's priced.
- **Actual:**
  - The market is created with state **open** and "3 unpriced".
  - The only way to price it is "Enter price · Sandbox adapter": one selection at a time, and for each one the trader must type feed internals, a **Provider sequence** and an **External message ID**, which a merchant has no reason to know.
  - Selections are shown as `QA United (cmvlm97d…lcb71)`, with raw IDs.
- **Likely files:** `features/platform/trading/TradingDetailScreen.tsx`, `features/keystone/mutations/sportsbook.ts` (`createCatalogEvent` market status, `ingestSandboxPrice`). Add a trader price form that generates the sequence and message ID, and create markets as SUSPENDED until every selection is priced.

## Business sense (day one for a sportsbook operator)

- The operator path now works up to "result pending approval": onboarding (with QA-017), event, market, prices and result entry. The approval inbox (QA-016) is the last hard stop before grading and settlement. Retest grading, settlement and the ledger after it's fixed.
- Result entry before kick-off (QA-019) and markets opening unpriced (QA-020) are the riskiest gaps for a real book: they let bets be accepted at no price and graded before the event.
- With the customer side closed (QA-004), the configured brand (QA-018), the priced event and the promotions can't be seen by any customer. If the owner keeps production closed, the storefront should at least show the operator's brand and "coming soon", not the generic "SPORTSBOOK".
- There's still no real payment-provider path (wallet is practice funds), which is consistent with the README's practice-play position.
