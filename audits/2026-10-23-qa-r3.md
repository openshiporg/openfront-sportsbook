## Blockers

### QA-028: Result approvals can't be approved: the request carries no body, so the inbox only offers Reject
- **Area:** dashboard
- **URL:** `/dashboard/platform/results`, then `/dashboard/platform/approvals`
- **Steps:**
  1. As QA Admin, take an event through LIVE and ENDED and close its market, then on Result approval set the outcomes and click **Enter pending result** ("Pending result version entered.").
  2. Under Pending, enter a reason and click **Request independent approval** ("approval pending · Decided by another user").
  3. Sign in as QA Approver (MFA verified) and open **Approval inbox**.
- **Expected:** the request shows the submitted result document, and the Decision select offers "Approve this exact body" and "Reject".
- **Actual:** the card says "**Body not recorded** · Reject and ask for resubmission.", EXPIRES says "Not recorded", and the Decision select has only **Reject**. Every result request created from the Results screen behaves this way (seen on the round 2 request and on a new one this round). The result can't be approved, so Grading stays "0 ready", Settlement stays "0 ready · No READY plans", and no wager can ever be graded or paid out.
- **Cause:** `features/keystone/mutations/sportsbook.ts:183` `requestResultApproval` creates `approvalRequest.create({ data: { tenantId, action: 'APPROVE_RESULT', payloadHash, requesterId, status: 'PENDING', reason } })` **without `requestPayload` (and without `expiresAt`)**. `features/platform/approvals/screens/ApprovalsPageClient.tsx:75` shows "Approve this exact body" only when `item.body !== null`. Store the canonical result document (the payload whose hash is `resultApprovalHash(result)` in `features/sportsbook/domain/result-approval.ts`) plus an expiry, as the other dual-control requests do. Then retest approval, then grading (`/dashboard/platform/grading`), then settlement.
- **Note:** request `cmvlswsh…ab2fa` for QA Rovers v QA Athletic is still pending. After the fix, reject it and request again so the new request has a body.

## Major

### QA-029: The trading status history misses the close when an event ends, and a redundant close reports success
- **Area:** dashboard (trading audit)
- **URL:** `/dashboard/platform/trading`, then `/dashboard/platform/trading/cmvlspkqt000ypc010tawoczj`
- **Steps:**
  1. With the market open, use Event clock & state to set the event to LIVE, then ENDED.
  2. Open the market. It now reads "moneyline · closed · v3" (ENDED closed it).
  3. Set New state to **Closed**, enter a reason, and click **Apply state change**.
- **Expected:** the Status history has a row "open → closed · Event ended" (source: event state, actor QA Admin). A Closed request on a market that's already closed is refused ("Market already closed") or is a recorded no-op.
- **Actual:** Status history still lists only 2 rows ("created → suspended", "suspended → open"). There's no record of the market closing, although its version went from 2 to 3. Step 3 says "Market state changed and recorded." and nothing new appears.
- **Why it matters:** the market's status history is the trading audit trail a regulator or dispute team reads ("when did this market stop taking bets?"). Today the most important transition is missing.
- **Likely files:** the event-state mutation in `features/keystone/mutations/sportsbook.ts` / `sportsbook-full.ts` (the "safety action" that closes markets on ENDED should write the same `MarketStatus` history record as `setMarketStatus`), and `setMarketStatus` (refuse or no-op when `status === current`).
